# Professor Messer 2.1 | Threat Actors

Threat actors are entities that cause security events. They are typically categorized by their location, resource levels, technical sophistication, and intent/motivation.

---

## Types of Threat Actors

### 1. Nation State
* **Location:** External
* **Resources:** Extensive (almost unlimited funding, people, and time)
* **Sophistication:** Very High

### 2. Organized Crime
* **Location:** External
* **Resources:** Extensive (highly funded and structured)
* **Sophistication:** Very High
* **Motivations:** Strictly financial profit.
* **Key Characteristics:** They operate like a corporate enterprise, often utilizing division of labor (e.g., dedicated exploit developers, data brokers, and even customer support reps for handling ransomware collections).

### 3. Insider Threat
* **Location:** Internal
* **Resources:** Utilizes existing corporate infrastructure/resources
* **Sophistication:** Medium
* **Motivations:** Financial gain, data theft, or professional/personal revenge.
* **Key Characteristics:** Highly dangerous because they are already authenticated and have bypassed external perimeter defenses.

### 4. Hacktivist
* **Location:** Typically External
* **Resources:** Limited funding / independent
* **Sophistication:** Can be quite high
* **Motivations:** Political, ideological, or philosophical reasons.
* **Key Characteristics:** Attacks are designed to draw public attention, frequently taking the form of website defacement, publicity stunts, or Distributed Denial of Service (DDoS) campaigns.

### 5. Unskilled (Script Kiddies)
* **Location:** External or Internal
* **Resources:** Limited
* **Sophistication:** Low
* **Motivations:** Broad disruption, minor data access, thrill-seeking, or personal satisfaction.
* **Key Characteristics:** Do not possess a deep understanding of the underlying software vulnerabilities; instead, they run pre-written, automated scripts or utilities found online.

### 6. Shadow IT
* **Location:** Internal
* **Resources:** Limited department budgets
* **Sophistication:** Low IT/Security sophistication
* **Motivations:** Convenience, productivity, and getting work done faster by bypassing rigid protocols.
* **Key Characteristics:** Non-malicious internal users who deploy unauthorized cloud infrastructure, software, or hardware tools without the explicit approval or knowledge of the central IT security team.



# Professor Messer 2.2 | Common Threat Vectors

> [!NOTE] Definition
> A **threat vector** (or attack vector) is the specific path, method, or mechanism an adversary uses to gain unauthorized access to a system, network, or server.

---

### 1. Messaging-Based Vectors

Communication platforms are prime targets because attackers leverage built-in user trust.

* **Email:**
  * **Phishing:** Spoofed communications that trick users into entering credentials on cloned landing pages.
  * **Payload Delivery:** Malicious links or weaponized file attachments.
  * **Social Engineering:** Fake invoice scams and fraudulent cryptocurrency schemes.
* **SMS (Smishing):** Urgent text messages impersonating delivery services, banks, or official bodies to induce link clicks.
* **Direct Messaging (IM):** Social engineering conducted via instant messengers and enterprise chat platforms.

---

### 2. Image & File Vectors

> [!WARNING] Active Content in Passive Formats
> Many modern media formats are not just static binary data—they can execute code or contain embedded objects.

* **Scalable Vector Graphics (SVG):**
  * Built using **XML** syntax.
  * Allows direct embedding of executable scripts (e.g., JavaScript).
  * Can trigger **Cross-Site Scripting (XSS)** vulnerabilities when rendered by a web browser.
* **Container & Complex Formats:**
  * **PDF Documents:** Act as object containers capable of hosting interactive scripts, multimedia, and external links.
  * **Compressed Archives (`.zip`, `.rar`):** Used to obscure malicious binaries from basic email/network scanners by nesting files inside deep directories.
* **Office Documents & Browser Extensions:**
  * **Macros:** Embedded automation code in spreadsheets or text documents repurposed to extract credentials or download secondary payloads.
  * **Add-ins/Extensions:** Rogue extensions possessing broad permissions to intercept web traffic and harvest data.

---

### 3. Voice & Telephony Vectors

* **Vishing (Voice Phishing):** Direct voice calls spoofing help desks, financial institutions, or executives to elicit sensitive data.
* **SPIT (Spam over Internet Telephony):** Automated, high-volume VoIP spam and robocall campaigns.
* **War Dialing:** Automated dialing sequences used to identify unprotected modems, remote maintenance ports, or open PBX systems.

---

### 4. Physical & Removable Media Vectors

> [!IMPORTANT] Perimeter Bypass
> A cheap physical device can entirely circumvent perimeter defenses, firewalls, and air gaps.

* **USB Drop Attacks:** Leaving flash drives in parking lots or common areas to entice employees into connecting them to internal network workstations.
* **Human Interface Device (HID) Emulation:** Microcontrollers programmed to impersonate keyboards (e.g., BadUSB). When plugged in, they automatically inject keystrokes and run terminal commands at superhuman speed.
* **Data Exfiltration:** High-capacity flash media used by malicious insiders or physical intruders to copy proprietary data directly without triggering network alerts.

---

### 5. Application & Software Architecture

* **Centralized / Web-Based Applications:**
  * Compromising a central multi-tenant server or hosted application instantly affects all connecting client instances.
* **Patch Management & EOL Systems:**
  * **Known Vulnerabilities:** Publicly documented CVEs that remain unpatched.
  * **Unsupported / Legacy Systems:** Hardware or operating systems that have reached End-of-Life (EOL) receive zero security updates, leaving vulnerabilities permanently open.
  * **Inventory Control:** Shadow IT and uncataloged devices operating under desks or forgotten in racks represent severe unmonitored risk.

---

### 6. Network & Wireless Infrastructure

* **Wireless Vulnerabilities:**
  * Weak or legacy protocols (WEP, WPA, WPA2) are vulnerable to cracking; enterprise environments require **WPA3** and **802.1X** authentication.
  * **Rogue APs:** Unauthorized access points connected to internal switch ports without IT oversight.
* **Bluetooth Exploitation:** Used for localized device discovery, tracking, and exploiting vulnerabilities in unpatched Bluetooth software stacks.
* **Open Service Ports:**
  * Each active network service (e.g., TCP 80, 443) expands the attack surface.
  * Unnecessary ports must be closed or protected using port-based or application-aware firewalls.
* **Default Credentials:**
  * Embedded systems, routers, and IP cameras often ship with public default credentials (e.g., `admin:admin`).
  * Systems not forced to rotate credentials upon setup are trivially compromised via public lookup databases.

---

### 7. Supply Chain Vectors

> [!DANGER] Upstream Exploitation
> Gaining access to a single supplier, managed service, or manufacturer provides a pathway into hundreds of downstream client environments.

* **Managed Service Providers (MSPs) & Contractors:**
  * Third-party contractors (e.g., HVAC vendors, remote IT support) often retain persistent administrative access to client networks. Compromising the vendor provides pivot access to the target network.
* **Tampered & Counterfeit Hardware:**
  * Counterfeit networking gear (e.g., modified switches) with weaponized firmware installed during assembly or transit.


# Professor Messer 2.2 | Phishing

> [!NOTE] Definition
> **Phishing** is a form of social engineering that uses various communication channels (email, SMS, voice, etc.) to deceive individuals into believing a request is legitimate, enticing them to disclose sensitive information, credentials, or personal data.

---

### 1. Core Mechanics & Indicators

Attackers prey on user trust in routine communications to elicit action.

* **Primary Objectives:**
  * **Credential Harvesting:** Capturing usernames and passwords via fraudulent landing pages mimicking legitimate login portals (e.g., email or banking interfaces).
  * **Malware Delivery:** Directing victims to compromised or attacker-controlled websites that silently download secondary malicious software.
  * **Identity Theft & Account Takeover:** Gaining email access to intercept password reset links (e.g., for PayPal or banking services) and search through stored personal data.
* **Common Red Flags:**
  * **Inconsistencies:** Subtle layout defects, unexpected fonts, or awkward spacing in the message or landing page.
  * **Urgency & Artificial Deadlines:** Threats of service disruption or account suspension if action is not taken immediately.
  * **Sender Mismatches:** Sender addresses originating from unrelated third-party services (e.g., an iCloud address sending a notification about a Rackspace account).

---

### 2. Common Deception Techniques

> [!WARNING] Visual Deception
> Attackers rely heavily on deceptive domains and fabricated scenarios to make fraudulent communications seem plausible.

* **Typosquatting (URL Hijacking):**
  * Registering domain names that closely resemble legitimate targets with subtle spelling alterations (e.g., `professormesser.com` vs. `professormesser.com`).
  * Relies on human error and casual observation where a user overlooks missing or swapped characters.
* **Pretexting:**
  * The deliberate fabrication of an elaborate, invented scenario or cover story to manipulate the victim into complying.
  * *Example:* Posing as a credit card fraud department claiming an automated utility payment failed, creating panic to extract payment details.

---

### 3. Phishing Variations by Channel

* **Smishing (SMS Phishing):**
  * Delivered via Short Message Service (SMS) directly to mobile devices.
  * Commonly impersonates postal/courier tracking services (e.g., USPS delivery suspensions due to incorrect address information) to prompt link clicks.
* **Vishing (Voice Phishing):**
  * Phishing conducted over phone calls, often using spoofed caller ID numbers.
  * Attackers impersonate authoritative entities (banks, tech support, government bodies) to coerce the victim into verbally sharing verification codes or account numbers.

---

### 4. Additional Fraud Patterns

* **Verification Code Scams:** Tricking targets into disclosing one-time MFA/2FA codes over the phone or chat to bypass multi-factor authentication controls.
* **Fake Check & Invoice Scams:** Sending fraudulent payment requests or advance-fee scams to compromise accounts or secure unauthorized wire transfers.

# Professor Messer 2.2 | Impersonation

> [!NOTE] Definition
> **Impersonation** is a social engineering attack where an adversary pretends to be someone else (a trusted coworker, executive, technical support agent, or official agency) to gain the victim's trust and manipulate them into divulging sensitive data or granting unauthorized access.

---

### 1. Social Engineering & Trust Tactics

Attackers use specific psychological angles and pretexts to bypass standard skepticism.

* **Internal Authority & Rank:**
  * Posing as high-ranking personnel (e.g., Vice President of Finance or Operations) to intimidate subordinates into complying quickly without questioning the request.
* **Familiarity & Peer Association:**
  * Claiming to be from the internal IT help desk or support staff. The assumption of working for the same organization establishes immediate rapport.
* **Technical Jargon & Complexity:**
  * Using sophisticated terminology or complex explanations to overwhelm targets, shifting their focus toward understanding the terms rather than verifying the caller's identity.

---

### 2. Information Elicitation

> [!WARNING] The Art of Elicitation
> Attackers rarely demand sensitive details upfront; they wrap requests inside crafted cover stories (pretexting) to make the data request seem urgent and logical.

* **Methodology:** Often conducted via voice calls (Vishing) where the attacker guides the conversation toward a specific operational problem (e.g., failed vendor payments, urgent software diagnostics).
* **Target Information:**
  * Bank account and routing numbers
  * Social Security Numbers (SSNs) and birth dates
  * User credentials and system access tokens
  * Credit card details

---

### 3. Identity Fraud & Downstream Exploitation

Once an attacker harvests personal identifiable information (PII), they use it to impersonate the victim in financial and legal contexts.

* **Credit & Loan Fraud:**
  * Opening new credit card accounts or taking out bank loans in the victim’s name, diverting physical cards/funds to attacker-controlled addresses, and abandoning the debt.
* **Illicit Banking Infrastructure:**
  * Creating checking or savings accounts under the victim’s identity to launder or store proceeds from other cybercrimes.
* **Tax & Benefit Fraud:**
  * Filing fraudulent tax returns using the victim’s SSN early in the tax season to divert refund payments into the attacker’s account before the legitimate owner files.

---

### 4. Prevention & Countermeasures

> [!IMPORTANT] Never Take Callers at Face Value
> Trust must always be verified through known, out-of-band channels before sharing sensitive details.

* **Never Volunteer Sensitive Data:** Legitimate support desks and administrators do not need your password or personal credentials to fix computer or network issues.
* **Withhold PII:** Refuse to disclose addresses, SSNs, dates of birth, or account details over inbound phone calls or unverified emails.
* **Independent Callback Verification:**
  * If a caller claims to represent a bank, vendor, or internal department, hang up and initiate a callback using an established, publicly published phone number or internal corporate directory.
  * Establish out-of-band identity verification as standard operational policy across the organization.

# Professor Messer 2.2 | Watering Hole Attacks

> [!NOTE] Definition
> A **watering hole attack** is a targeted security exploit where an adversary identifies, compromises, and injects malware into a third-party website frequently visited by members of a targeted organization, waiting for the targets to visit the site and become infected.

---

### 1. Attack Mechanics & Strategy

When direct attacks fail because an organization has hardened defenses and trained employees (e.g., staff who refuse to click suspicious email links or pick up dropped USB drives), attackers pivot to indirect pathways.

* **Reconnaissance:**
  * Attackers research the target organization to discover legitimate third-party websites commonly visited by its employees.
  * *Examples:* Industry news portals, specialized discussion forums, or even mundane daily sites like local sandwich and coffee shop ordering portals.
* **Compromise the "Watering Hole":**
  * The attacker finds vulnerabilities in the third-party site or exploits their infrastructure (via web server vulnerabilities, phishing their staff, etc.).
  * Malicious payloads (such as injected JavaScript, drive-by download scripts, or redirect code) are planted on the compromised server.
* **Waiting for the Target:**
  * Rather than launching outbound attacks, the attacker waits passively for target employees to visit the compromised site during normal business operations.

---

### 2. Targeted Delivery & Evasion

> [!WARNING] Selective Poisoning
> Modern watering hole attacks do not always infect every visitor; doing so increases the likelihood of rapid detection.

* **IP Filtering & Geo-targeting:**
  * Attackers inspect the visitor's source IP address or HTTP headers.
  * If the visitor belongs to the target organization's IP address blocks (e.g., specific banks or enterprise ranges), the server serves the malicious script.
  * All other general visitors receive the clean, normal version of the website, keeping the compromise hidden from webmasters and casual scanners.
* **Real-World Case Study (January 2017):**
  * Attackers compromised regulatory sites, including the Polish Financial Supervision Authority, Mexico's National Banking and Stock Commission, and a state-owned bank in Uruguay.
  * Malicious JavaScript was served exclusively to visitors originating from specific financial institutions and banks, leaving the site completely normal for the general public.

---

### 3. Prevention & Mitigation

No single security control can prevent a watering hole attack because the initial compromise occurs on external infrastructure outside the organization's control.

> [!IMPORTANT] Defense-in-Depth
> Protecting against watering hole attacks requires layered controls where multiple independent security mechanisms operate concurrently.

* **Layered Defenses:**
  * **Firewalls & Web Content Filtering:** Filter and inspect outbound web requests and block traffic to untrusted or newly categorized malicious domains.
  * **Intrusion Prevention Systems (IPS):** Deep packet inspection analyzes the actual payload/content passing through allowed ports (e.g., HTTP/HTTPS) to identify exploit signatures and malicious code patterns.
  * **Endpoint Antivirus / EDR:** Host-level endpoint protection intercepts malicious scripts, suspicious browser behavior, and dropped payloads if network perimeter inspection fails.

  * Activity monitoring and browsing history tracking.
  * Unauthorized data exfiltration to attacker-controlled infrastructure.

# Professor Messer 2.3 | Memory Injections

> [!NOTE] Definition
> **Memory injection** is an attack technique where malicious code is inserted directly into the memory space of an existing, legitimate running process to execute payloads covertly and inherit the target process's privileges.

---

### 1. Memory Execution & Attack Objectives

All software—including malware—must load from storage into RAM to be executed by the CPU. In Windows environments, memory hosts running threads, buffers, management functions, and Dynamic Link Libraries (DLLs).

* **Independent vs. Injected Processes:**
  * Malware can attempt to spin up as an independent process, but this is easily spotted by task managers and endpoint detection tools.
  * Instead, attackers inject malicious instructions into the allocated address space (between the starting and ending memory addresses) of a trusted, legitimate application.
* **Key Tactical Advantages:**
  * **Evasion:** Bypasses basic antimalware scanners that look exclusively for unfamiliar or rogue process names.
  * **Privilege Escalation:** Injected code inherits the security context, rights, and access tokens of the parent process it compromises (e.g., system-level or administrative rights).

---

### 2. DLL Injection (Dynamic Link Library Injection)

> [!WARNING] Shared Library Abuse
> DLLs contain reusable, shared code and functions that multiple applications can call simultaneously. Attackers take advantage of this modular architecture to force valid processes to load rogue libraries.

* **Step-by-Step Attack Mechanism:**
  1. **Placement:** The attacker drops a malicious DLL onto a local or accessible shared storage volume.
  2. **Pointer / Path Modification:** The attacker modifies or injects a file path pointing to the malicious DLL into the target application’s running memory space.
  3. **Execution via Legitimate Process:** As the host process executes and reaches the injected reference, it makes a standard library call to disk.
  4. **Memory Load:** The operating system loads the malicious DLL into memory under the umbrella of the legitimate process, successfully running the payload.

# Professor Messer 2.3 | Buffer Overflows

> [!NOTE] Definition
> A **buffer overflow** occurs when an application writes more data to an allocated memory buffer than it was designed to hold, causing the excess data to spill over into adjacent memory spaces and overwrite other variables, pointers, or instructions.

---

### 1. Root Cause & Exploitation Dynamics

* **Lack of Bounds Checking:** Developers fail to properly sanitize or restrict user input, allowing inputs that exceed the allocated memory size (e.g., inputting 9+ bytes into an 8-byte space).
* **Exploitation Challenges:**
  * Buffer overflows are volatile vulnerabilities. Arbitrary data spills often corrupt critical pointers, causing the application or operating system to crash immediately (Denial of Service).
  * Attackers search for a **repeatable and reliable** exploit—inserting specific, crafted payloads into exact memory offsets to alter program execution rather than crashing it.

---

### 2. Attack Example: Privilege Escalation via Overflow

> [!WARNING] Overwriting Adjacent Variables
> By precisely calculating byte lengths, an attacker can intentionally overwrite the value of an adjacent variable that controls security privileges.

* **Initial Memory State:**
  * **Variable A:** User input buffer allocated **8 bytes** (initially empty / all zeroes).
  * **Variable B:** Adjacent **2-byte** permission flag stored directly after Variable A.
    * Current Value: `1979` (decimal), representing standard **user/guest** access (any value `< 2000`).
    * Target Value: Any value `> 24000` grants **administrative** privileges.
    * Under normal operation, users cannot modify Variable B directly.
* **The Overflow Execution:**
  * The attacker inputs the 9-letter string `"EXCESSIVE"` into Variable A.
  * The first 8 bytes (`EXCESSIV`) completely fill Variable A's allocated buffer.
  * The 9th byte (`E`, hexadecimal `0x65`) overflows into the first byte of **Variable B**.
* **Outcome:**
  * The value of Variable B shifts from `1979` to `25856`.
  * Because `25856 > 24000`, the application grants the attacker full administrative permissions without requiring valid admin credentials.

# Professor Messer 2.3 | Race Conditions

> [!NOTE] Definition
> A **race condition** occurs when two or more software threads, processes, or actions execute concurrently and attempt to access or modify shared resources at nearly the same time, producing unintended, inconsistent, or insecure results because the application failed to sequence the operations properly.

---

### 1. Time-of-Check to Time-of-Use (TOCTOU)

> [!WARNING] The Window of Vulnerability
> A TOCTOU attack exploits the gap in time between when a system verifies a condition or value and when it actually performs an action based on that value. If an attacker alters the underlying data during this window, the application proceeds under false assumptions.

* **Check Phase:** The application queries a file, permission, or account balance.
* **Vulnerable Window:** Another thread, user, or malicious script modifies that value before execution completes.
* **Use Phase:** The application executes its task using outdated information from the check phase, leading to privilege escalation, corrupted state, or unauthorized actions.

---

### 2. Practical Example: Bank Balance Race Condition

Consider two users (User 1 and User 2) transferring money concurrently between two accounts (Account A and Account B), each starting with $100. The application updates deposits immediately, but delays synchronizing withdrawals across concurrent sessions.

1. **Initial State:** Account A = $100 | Account B = $100.
2. **Concurrent Checks:** Both users check balances simultaneously; both read $100 in each account.
3. **Deposits Executed:**
   * User 1 deposits $50 to Account B $\rightarrow$ Account B = $150.
   * User 2 deposits $50 to Account B $\rightarrow$ Account B = $200.
4. **Withdrawals Executed:**
   * User 1 withdraws $50 from Account A $\rightarrow$ User 1's view: Account A = $50.
   * User 2 simultaneously withdraws $50 from Account A before the ledger syncs across sessions $\rightarrow$ User 2's session also subtracts from $100, recording Account A = $50 instead of updating the already-reduced balance.
5. **Final Flawed State:** Account A ends with $50 and Account B with $200 (totaling $250 instead of the original $200). Account A should have been reduced to $0, creating extra money out of thin air due to unsynchronized operations.

---

### 3. Real-World Case Studies

* **Mars Rover *Spirit* (2004):**
  * A file system error triggered an automated fail-safe designed to reboot the rover whenever a critical error occurred.
  * During the reboot sequence, the rover immediately re-checked the file system, encountered the same unresolved error, and initiated another reboot before the error-handling process could stabilize.
  * This created an infinite reboot loop until NASA engineers transmitted override code to break the cycle.
* **Tesla Model 3 / Pwn2Own Vancouver (2023):**
  * Security researchers identified a TOCTOU race condition in the Tesla Model 3 infotainment system reachable via Bluetooth.
  * Exploiting the timing window enabled privilege escalation to full `root` access, winning the researchers a $100,000 prize and the vehicle itself.

# Professor Messer 2.3 | Malicious Updates

> [!NOTE] Definition
> **Malicious updates** occur when an attacker introduces unauthorized, malicious code into the update cycle of an application or operating system. Because applying patches is a fundamental security best practice, attackers attempt to exploit that implicit trust to distribute malware widely.

---

### 1. Update Risks & Verification

Applying patches updates or replaces program files—meaning every update is effectively the installation of new software.

* **Fake Update Prompts:**
  * Attackers frequently use browser pop-ups or poisoned search results that warn a user their browser or software is "outdated" (e.g., fake Google Chrome update banners).
  * Clicking these prompts downloads a malicious payload disguised as a patch installer.
* **Update Verification Best Practices:**
  * **Always Backup First:** Maintain up-to-date system backups before patching to quickly roll back if an update corrupts the environment or introduces stability issues.
  * **Direct Developer Sourcing:** Never download updates from unverified third-party hosts or contextual web pop-ups; obtain them directly from the official vendor portal.
  * **Digital Signatures:** Operating systems check code-signing certificates to ensure files originate from a verified publisher (e.g., Microsoft, Google, Adobe) and have not been altered in transit.
  * **Native In-App Updaters:** Built-in auto-update mechanisms inside applications carry higher trust because the app automatically retrieves and cryptographically verifies the update package.

---

### 2. Supply Chain Compromise: SolarWinds Orion

> [!DANGER] Upstream Code Injection
> Even cryptographically signed, automated, in-app updates are vulnerable if an adversary breaches the vendor’s internal development or build pipeline.

* **Incident Overview (December 2020):**
  * Attackers infiltrated the software development and build environment of **SolarWinds**, an enterprise network and infrastructure management vendor.
  * The attackers injected a backdoor directly into the source code of the **SolarWinds Orion** management platform months before release.
* **The Distribution Vector:**
  * The malicious code was automatically compiled, built, and digitally signed with SolarWinds' legitimate corporate certificate.
  * The tainted package was pushed out across the standard, trusted automatic update mechanism to customers worldwide.
* **Impact & Blast Radius:**
  * High-profile government agencies and Fortune 500 enterprises running Orion received the validly signed malicious update.
  * Because Orion requires extensive administrative rights to monitor network infrastructure, adversaries gained deep footholds, allowing them to pivot internally to other critical systems across affected networks.


# Professor Messer 2.3 | Operating System Vulnerabilities

> [!NOTE] Definition
> Operating systems serve as the foundational computing layer for nearly every device. Because of their massive scale and universal usage, they represent high-value targets for threat actors seeking footholds to exploit underlying systems.

---

### 1. Operating System Complexity & Unknown Vulnerabilities

Modern operating systems contain vast codebases (e.g., Windows 11 contains an estimated tens of millions of lines of code).

* **The Codebase Scale Problem:** Greater volume and complexity in code inherently create more potential coding errors, logic flaws, and exploitable security gaps.
* **Latent (Undiscovered) Flaws:** Every currently deployed operating system harbors undiscovered vulnerabilities that have simply not yet been found or disclosed by security researchers or threat actors.
* **Vulnerability Lifecycle:** Once researchers or vendors identify an issue, the vendor develops a remediation patch and publishes it during routine or out-of-band updates.

---

### 2. Microsoft Patch Tuesday & Common Vulnerability Types

> [!WARNING] The Post-Disclosure Race
> Microsoft releases scheduled updates on **Patch Tuesday** (the second Tuesday of every month). Once patches are published, threat actors immediately reverse-engineer the fixes to create exploit code targeting systems that have not yet updated.

A single monthly update cycle can resolve dozens to nearly a hundred individual vulnerabilities. Common vulnerability classifications addressed in these patches include:

* **Remote Code Execution (RCE):** Flaws that allow an attacker to run arbitrary instructions on a target machine over the network without requiring physical access.
* **Elevation of Privilege (EoP):** Flaws permitting a standard or guest user account to gain administrative or kernel/SYSTEM-level permissions.
* **Security Feature Bypass:** Weaknesses that allow an adversary to circumvent native defensive controls (such as authentication or encryption checks).
* **Reference Resource:** Patches, vulnerability details, and Common Vulnerabilities and Exposures (CVE) trackers can be reviewed via the Microsoft Security Response Center (`msrc.microsoft.com`).

---

### 3. Patching Best Practices & Operational Strategy

Enterprise environments must strike a balance between prompt remediation and operational stability.

* **Rapid Deployment:** Apply patches as quickly as possible following public release to shrink the window of opportunity for reverse-engineered exploits.
* **Pre-Deployment Testing:** In enterprise environments with hundreds or thousands of endpoints, test patches in a staging environment prior to full rollout to verify they do not break business-critical applications.
* **Handling Reboots:** Core kernel and OS service updates often require a full system restart to swap in the updated binaries; coordinate reboots to avoid data loss or production disruption.
* **Known Good Backups:** Always take verifiable system backups before applying major OS updates or service packs so machines can be restored to a known stable state if an update causes unexpected failures.



# Professor Messer 2.3 | SQL Injection

SQL injection (SQLi) is a code injection technique where an attacker inserts malicious Structured Query Language (SQL) statements into an application input field. This manipulates backend database queries, allowing the attacker to bypass authentication, view unauthorized records, modify data, or destroy database tables.

---

### 1. Code Injection Overview

* Vulnerability Cause: Occurs when application developers fail to implement proper input validation, bounds checking, or sanitization on user-supplied data before passing it to backend interpreters.
* Common Injection Types: SQL injection, HTML injection, and XML injection.
* Low Barrier to Entry: Attacks can be executed directly inside a web browser by typing payloads into everyday text boxes, login fields, or search bars without writing custom software.

---

### 2. Mechanics of a SQL Injection

> [!WARNING] Tautology Manipulation
> Attackers manipulate SQL boolean logic using tautologies (statements that always resolve to true) to bypass filters and force the database to return all stored rows.

* Normal Query Logic:
  SELECT * FROM users WHERE name = Professor
  The database looks strictly for records where the name field matches the search string.

* Injected Query Logic:
  SELECT * FROM users WHERE name = Professor OR 1 = 1
  Because 1 always equals 1, the entire conditional statement evaluates to true for every single row in the database, causing the engine to dump all records in the table.

---

### 3. Practical Example: WebGoat

Using the intentionally vulnerable training platform WebGoat:

* Standard Authentication Lookup:
  * User inputs: Name = Smith, Authentication Number = 3SL99A
  * Result: The application strictly returns the single department record assigned to Smith with that matching authentication key.

* Injected Tautology Exploit:
  * User inputs: Name = Smith, Authentication Number = OR 1 = 1
  * Result: The query checks whether the authentication key matches OR if 1 equals 1. Because 1 equals 1 is universally true, the database outputs every employee name, department, and authentication key stored across the entire database.

---

### 4. Impact & Consequences

> [!DANGER] Complete Database Control
> Executing an injection attack completely circumvents application-level security and permission layers.

* Data Disclosure: Exfiltrating confidential database tables, user passwords, personally identifiable information, and financial details.
* Data Manipulation: Altering existing tables, modifying balances, or injecting false transactions.
* Data Destruction: Dropping entire databases or deleting critical system tables.
* Denial of Service: Overloading database processing resources or wiping underlying storage to make services unavailable.


# Professor Messer 2.3 | Cross-site Scripting

Cross-site scripting (XSS) is a web application vulnerability where an attacker injects malicious client-side scripts, typically written in JavaScript, into trusted websites. When a victim accesses the affected web page, their browser executes the script under the assumption that it originated from a trusted source, allowing the attacker to steal session tokens, hijack cookies, or compromise user accounts.

---

### 1. Overview & Core Mechanics

* Naming: Abbreviated as XSS rather than CSS to prevent confusion with Cascading Style Sheets.
* Target of Exploitation: Takes advantage of the implicit trust a user's web browser places in a legitimate, reputable website.
* Primary Vector: Injected JavaScript executed locally within the victim's browser session.
* Attacker Objectives: Stealing session tokens, exfiltrating authentication cookies, capturing credentials, or performing unauthorized actions on behalf of the victim.

---

### 2. Primary XSS Attack Types

> [!WARNING] Reflected vs. Stored Payloads
> Cross-site scripting vulnerabilities are categorized primarily by whether the injected malicious script is immediately bounced back to a single user or permanently saved on the target web server.

* Non-Persistent (Reflected) XSS:
  * The malicious script is embedded directly into a crafted link, search field, or form submission.
  * The attacker tricks the victim into clicking the link via email, SMS, or social media.
  * When the victim visits the link, the vulnerable web server reflects the unvalidated input back to the user's browser, executing the script.
  * Impact: Primarily affects the specific individual who clicks the crafted link.

* Persistent (Stored) XSS:
  * The attacker submits malicious script payloads into input fields permanently stored by the server (e.g., forum posts, product reviews, or social media comments).
  * Anyone who navigates to that page or feed automatically downloads and runs the payload in their local browser.
  * Propagation: Attackers can design the script to auto-repost itself to other users' profiles, creating an automated, worm-like viral spread.

---

### 3. Real-World Case Study: Subaru Web Portal (2017)

Security researcher Aaron Guzman discovered an XSS exploit on Subaru's connected vehicle web management portal:

* The Vulnerability: Inadequate input validation on the web management portal allowed an attacker to execute a cross-site scripting attack against registered owners.
* The Flawed Architecture: Authentication tokens generated upon logging into the portal never expired and had unlimited capabilities to perform service requests on vehicles.
* The Exploit Chain: An attacker could use XSS to steal an owner's permanent authentication token, grant the attacker persistent access, and even add the attacker's email to authorize control over additional vehicles.

---

### 4. Prevention & Countermeasures

> [!IMPORTANT] Input Sanitization and Secure Development
> Securing web applications against XSS requires rigorous input filtering on the server side along with safe browser habits on the client side.

* Secure Coding Practices:
  * Input Validation: Strictly validate, sanitize, and filter all incoming user inputs to reject executable tags and script elements.
  * Output Encoding: Encode dynamic output data before rendering it in the browser so that executable characters are treated strictly as inert text.
* Client-Side Defenses:
  * Avoid clicking unsolicited links in emails, text messages, or unverified communications.
  * Keep web browsers and operating systems fully patched against known DOM and script handling vulnerabilities.
  * Use browser controls or extensions to manage or restrict unnecessary script execution where appropriate.


# Professor Messer 2.3 | Hardware Vulnerabilities

Hardware vulnerabilities stem from physical and embedded devices connected to networks where users generally do not have direct access to the underlying operating system. Because these devices run specialized firmware developed solely by the original manufacturer, they present unique patching delays, lifecycle risks, and attack surfaces across both enterprise and home environments.

---

### 1. Embedded Systems & IoT Security

* The Scope of IoT: Modern environments connect everyday appliances and facility controls directly to IP networks (thermostats, time clocks, smart stoves, refrigerators, garage door openers, HVAC controls).
* The Firmware Challenge:
  * Embedded devices run vendor-specific firmware that abstracts the underlying OS away from the end user.
  * Users cannot independently inspect code, install custom patches, or harden the underlying OS.
  * System security depends entirely on the manufacturer's willingness and capability to discover, develop, and issue firmware updates.
* Slow Patch Turnaround (Case Study):
  * Trane ComfortLink II automated thermostats were reported to have security vulnerabilities in April 2014.
  * The manufacturer did not release an initial security patch until April 2015 (one full year later), followed by another in January 2016.
  * Unlike standard PC operating systems that receive monthly updates, embedded devices frequently leave known vulnerabilities exposed for prolonged periods.

---

### 2. Device Lifecycle: EOL vs. EOSL

> [!WARNING] Support Lifecycles
> Tracking hardware lifecycle milestones is critical for vulnerability management. Once vendor support terminates, newly discovered flaws remain permanent zero-days.

* End of Life (EOL):
  * The date when a manufacturer officially stops selling and marketing a product.
  * Security patches and software updates may still be developed and published during this transitional phase.
  * Serves as an early operational warning to begin budgeting and planning for hardware replacement.
* End of Service Life (EOSL):
  * The milestone where the vendor terminates all active maintenance, updates, and standard security patch releases.
  * Extended support contracts might be offered at exorbitant costs, but general updates cease.
  * Devices reaching EOSL should be prioritized for immediate decommission or replacement to eliminate unpatchable exposures.

---

### 3. Securing Legacy Platforms

> [!IMPORTANT] Mitigating Unreplaceable Systems
> Organizations often depend on legacy hardware or outdated applications that are critical to operational goals and cannot simply be powered off or easily replaced.

* Risk Assessment: Evaluate the business necessity of keeping legacy hardware online against the security liability of running unpatched firmware or obsolete middleware.
* Compensating Controls & Isolation:
  * Network Segmentation: Place legacy hardware into isolated VLANs with strictly regulated access.
  * Firewall Access Control: Implement restrictive ingress and egress firewall rules to limit which endpoints can communicate with the hardware.
  * Intrusion Prevention Systems (IPS): Apply specialized IPS signatures specifically targeted at detecting and blocking exploits aimed at older, known operating system flaws.
  * Phased Decommissioning: Maintain compensating protections while establishing a planned migration roadmap to modern, supported hardware.

# Professor Messer 2.3 | Virtualization Vulnerabilities

Virtualization and cloud infrastructures allow systems to instantiate and decommission virtual machines (VMs) dynamically. While guest operating systems require the same baseline security practices as physical endpoints, virtualization introduces unique attack surfaces tied to the underlying hypervisor, isolation mechanisms, and shared hardware resources.

---

### 1. Cloud & Virtualization Management Challenges

* Ephemeral Environments: Rapid provisioning and deprovisioning of VMs make tracking security baselines and configuration drift far more challenging than managing static physical hardware.
* Heterogeneous Configurations: VMs on the same physical host may run varying operating systems, allocated core counts, storage configurations, and patch levels.
* Shared Foundation: A guest OS still shares underlying vulnerabilities (local privilege escalation, command injection, information disclosure) with its physical counterparts, requiring standard host hardening and OS patch management.

---

### 2. VM Escape Attacks

> [!DANGER] Breaking Hypervisor Isolation
> Under normal operation, the hypervisor isolates guest VMs into self-contained sandboxes with dedicated virtual hardware boundaries. A VM Escape bypasses this containment, granting an attacker access to the host hypervisor or other guest VMs.

* Blast Radius: Because a single bare-metal hypervisor can host dozens or hundreds of tenant virtual machines, breaking isolation gives an attacker direct access to multi-tenant workloads, sensitive memory spaces, and private data across the host.
* Attack Chain Case Study (Pwn2Own March 2017):
  1. Edge Sandbox Escape: Attackers exploited a bug in the JavaScript engine of Microsoft Edge to break out of the browser's sandbox.
  2. Kernel Privilege Escalation: Exploited a vulnerability in the Windows 10 guest kernel to achieve full administrative control of the guest VM.
  3. Hypervisor Breakout: Exploited a hardware simulation vulnerability in VMware to escape the guest VM and access other virtual machines residing on the shared hypervisor.

---

### 3. Resource Reuse & Memory Overcommit

> [!WARNING] Hypervisor Allocation Flaws
> Hypervisors rely on overcommitment—allocating more virtual memory or CPU capacity across VMs than physically exists on the hardware host—relying on dynamic reclamation to balance load.

* The Overcommit Model:
  * Example: A host with 4 GB of physical RAM dynamically supports three VMs configured with 2 GB of RAM each (6 GB total allocated), under the assumption that not all VMs consume their full capacity simultaneously.
* Information Disclosure Risk:
  * Because physical memory blocks are rapidly reassigned between different virtual instances, strict hypervisor-level memory scrubbing and boundary separation are required.
  * If the hypervisor contains memory management bugs, residual data written by one VM might persist in unscrubbed memory pages and be read by another VM sharing the same physical host.
* Mitigation: Regular hypervisor firmware and software patching to resolve low-level memory scheduling, isolation, and virtual hardware simulation bugs.



# Professor Messer 2.3 | Cloud-specific Vulnerabilities

Cloud-specific vulnerabilities arise from migrating critical applications, sensitive data, and infrastructure management consoles to public cloud environments. While public cloud platforms enable universal accessibility and rapid scaling, they expose organizations to a global attack surface where simple misconfigurations, lack of multi-factor authentication, and unpatched dependencies can lead to full tenant compromise.

---

### 1. Cloud Security Posture & Reality

* Public Exposure: Applications hosted in a public cloud are reachable by anyone on the internet, vastly expanding exposure to automated scanning, probing, and exploitation.
* MFA Deficiencies: Studies estimate that roughly 76% of organizations do not enforce multi-factor authentication (MFA) on their centralized cloud management consoles, leaving accounts vulnerable to credential stuffing and phishing.
* Unpatched Cloud Code: Up to 63% of cloud codebases contain unpatched vulnerabilities, many with Common Vulnerability Scoring System (CVSS) severity scores of 7.0 or higher (High to Critical).

---

### 2. Infrastructure & Architectural Attack Vectors

> [!WARNING] Global Attack Surface
> Public-facing cloud entry points allow adversaries worldwide to target weak access controls, misconfigurations, and availability bottlenecks.

* Denial of Service (DoS / DDoS): Universally accessible endpoints can be flooded with volumetric or application-layer traffic from distributed global botnets, degrading service availability or exhausting cloud billing budgets.
* Broken / Weak Authentication: Improperly configured identity and access management (IAM) rules or weak authentication mechanisms allow attackers to bypass login boundaries and access underlying data repositories.
* Misconfigurations & Directory Traversal:
  * Incorrectly configured web services or storage buckets permit directory traversal attacks, allowing adversaries to navigate beyond designated web roots into restricted filesystem directories and configuration files.
* Remote Code Execution (RCE): Running unpatched software or outdated container images lets attackers execute arbitrary shell commands directly on cloud compute instances.

---

### 3. Application-Level Vulnerabilities in the Cloud

> [!DANGER] Upstream Framework Exploitation
> Because cloud workloads rely heavily on modular frameworks and open-source libraries, a single vulnerability in a common dependency creates a direct pathway into the underlying hosting instance.

* High-Impact Library Exploits (Log4j & Spring Cloud):
  * Widespread vulnerabilities like Log4Shell (Log4j) and Spring Cloud Function exploits are trivial to automate and execute, requiring minimal attacker effort while granting unauthenticated remote code execution.
  * Exploiting these framework flaws provides a foothold to compromise the local container/instance and pivot laterally to other services in the virtual private cloud (VPC).
* Memory Flaws (Out-of-Bounds Write):
  * Flaws that allow attackers to write data outside allocated memory boundaries, leading to arbitrary code execution or system crashes (Denial of Service).
* Web & Database Exploits:
  * Cross-Site Scripting (XSS): Insufficient input sanitization enables attackers to inject client-side scripts to steal admin session tokens.
  * SQL Injection (SQLi): Bypassing application logic to query, alter, or dump backend cloud database instances hosting sensitive corporate or customer data.


# Professor Messer 2.3 | Supply Chain Vulnerabilities

Supply chain security encompasses every phase required to produce and deliver a finished product to the end consumer, from raw material procurement and manufacturing to distribution, third-party servicing, and software deployment. An exploit inserted at any point in this chain can bypass traditional perimeter defenses and compromise systems that trust the upstream provider.

---

### 1. Third-Party Service Providers & Lateral Pivoting

Organizations frequently outsource critical functions—including network management, accounting, facilities, utilities, cleaning, and cloud infrastructure—to third-party service providers.

* The Extended Attack Surface: Granting service providers remote or local network access means their security posture directly impacts your own. An attacker who compromises a vendor can inherit their trusted access into your internal infrastructure.
* Right to Audit & Continuous Auditing: Organizations should mandate regular third-party security audits in vendor contracts to verify compliance with organizational security baselines.
* Case Study (Target Breach, November 2013):
  * Over 40 million credit and debit card numbers were stolen from Target's point-of-sale (POS) systems.
  * Attackers initially compromised an external heating, ventilation, and air conditioning (HVAC) vendor in Pennsylvania via a phishing email containing malware.
  * The HVAC vendor held direct remote access to manage Target's environmental systems.
  * Target’s internal network was not segmented; the HVAC network shared the exact same subnet/access path as the POS registers.
  * Attackers pivoted from the compromised HVAC access directly onto register endpoints across nationwide stores, installing card-scraping malware.

---

### 2. Hardware Supply Chain & Counterfeit Devices

> [!WARNING] The Perils of Counterfeit Infrastructure
> Core routing and switching hardware processes all organizational traffic. Installing tampered or counterfeit equipment provides threat actors with built-in interception points.

* Untrusted Sourcing: Buying network or security hardware through unauthorized third-party gray-market channels creates massive operational and security exposure.
* Vetted Vendor Lists: Organizations should enforce strict procurement policies, limiting purchases exclusively to certified, authorized manufacturers and distributors.
* Case Study (DHS Cisco Reseller Bust, July 2022):
  * The Department of Homeland Security arrested a reseller who sold over $1 billion in counterfeit networking hardware disguised with genuine Cisco logos and branding.
  * The operation used roughly 30 shell companies operating since 2013 to distribute modified devices manufactured in China.
  * In addition to posing security backdoors, the counterfeit gear lacked proper quality controls, causing equipment to overheat, fail unexpectedly, and catch fire in production racks.

---

### 3. Software Supply Chain & Build-Pipeline Attacks

> [!DANGER] Weaponizing Trusted Upstream Updates
> Attackers target upstream development infrastructure so that malicious payloads are compiled, signed, and distributed through official, automated update channels.

* Implicit Trust in Updates: Organizations depend on code signing and automated update engines to patch systems rapidly. If the upstream repository or build pipeline is subverted, signatures will validate forged updates as authentic.
* Open-Source Risks: Having public visibility into open-source repositories allows both security reviews and threat actors looking to submit malicious pull requests or identify zero-day vulnerabilities.
* Case Study (SolarWinds Orion, 2020):
  * Attackers breached SolarWinds' internal build environment and injected a backdoor into the Orion network monitoring software.
  * Orion software packages were compiled, digitally signed with genuine SolarWinds certificates, and distributed through routine updates in March and June 2020.
  * The breach remained undetected for months until December 2020, granting adversaries persistent access across approximately 18,000 corporate and government networks (including Microsoft, Intel, Cisco, the Pentagon, and the US Department of the Treasury).


# Professor Messer 2.3 | Misconfiguration Vulnerabilities

Misconfiguration vulnerabilities occur when systems, applications, cloud services, or network devices are deployed with insecure default settings, improper access permissions, or unencrypted communications. These weaknesses represent low-hanging fruit for attackers because they require no specialized exploit code to access sensitive data or administrative controls.

---

### 1. Open Cloud Storage & Data Exposure

* Public Exposure: Cloud repositories (such as Amazon S3 buckets) are frequently configured with public read access or left entirely unauthenticated due to human error.
* Attacker Reconnaissance: Threat actors continually run automated scans searching for exposed cloud storage containing backups, databases, and customer records.
* Case Study (Verizon Records, June 2017):
  * A third-party vendor misconfigured an Amazon S3 storage repository, exposing over 14 million Verizon customer records publicly on the internet with no password or authentication required.
  * Discovered by a security researcher who coordinated remediation before malicious actors accessed the data.

---

### 2. Unsecured Administrative & Superuser Accounts

> [!WARNING] Superuser Exposure
> Root (Linux/Unix) and Administrator (Windows) accounts have unrestricted authority over the operating system. Leaving them accessible or poorly secured compromises the entire host.

* Weak & Predictable Passwords: While operating systems prevent blank passwords on administrative accounts, administrators often configure simple, common passwords (e.g., `123456`, `ninja`, `football`) vulnerable to brute-force and dictionary attacks.
* Best Practices for Privileged Accounts:
  * Disable Direct Root/Administrator Logins: Prevent users from logging in directly as the root/administrator account.
  * Privilege Escalation Mechanisms: Users log in with standard, least-privilege user accounts and elevate their permissions on-demand using tools like `sudo` / `su` on Linux or `Run as administrator` on Windows.
  * Minimize Privileged Accounts: Keep the total count of accounts granted administrative capabilities strictly limited.

---

### 3. Cleartext Protocols vs. Encrypted Alternatives

Encryption mechanisms provide no defense if communication relies on legacy protocols that transmit data over the wire unencrypted.

* Cleartext Protocols: Protocols like **HTTP**, **Telnet**, **FTP**, **SMTP**, and **IMAP** transmit usernames, passwords, cookies, and payloads in plain readable text.
* Network Sniffing: A packet capture tool (such as Wireshark) can capture and reconstruct cleartext sessions to harvest credentials.
* The "Wall of Sheep" (DEF CON): At the DEF CON hacking conference, network monitors observe cleartext traffic over conference Wi-Fi, projecting leaked usernames, partial passwords, and destination servers onto a public display to demonstrate the dangers of unencrypted protocols.
* Encrypted Replacements:
  * HTTP $\rightarrow$ **HTTPS**
  * Telnet $\rightarrow$ **SSH**
  * FTP $\rightarrow$ **SFTP / FTPS**
  * Cleartext Mail (IMAP/POP/SMTP) $\rightarrow$ **IMAPS / POPS / SMTPS** (TLS encrypted)

---

### 4. Default Credentials & IoT Botnets

> [!DANGER] Unchanged Factory Defaults
> Many networked appliances ship with standardized, publicly documented default usernames and passwords (e.g., `admin:admin`) that users neglect to change upon deployment.

* The Mirai Botnet:
  * Exploited over 60 hardcoded factory-default login pairs across Internet of Things (IoT) hardware (security cameras, DVRs, routers, smart doorbells).
  * Automatically scanned public IP ranges for open management ports, authenticated with default credentials, and enlisted compromised hardware into massive DDoS botnet swarms.
  * Released as open-source code, enabling both researchers and malicious adversaries to locate and compromise devices using default setups.

---

### 5. Open Ports & Firewall Rule Misconfigurations

* Service Attack Surface: Every enabled network service binds to a specific listening port (e.g., TCP 80, 443, 22), granting external clients a connection point into the server.
* Firewall Complexity:
  * Firewalls enforce access control lists (ACLs) based on source/destination IP addresses and port numbers.
  * Large, convoluted firewall rule bases frequently lead to configuration drift, accidental "allow-all" permissions, or forgotten testing rules that expose internal ports to the internet.
* Remediation: Conduct regular firewall rule base audits to verify business justification for every open port and prune obsolete allowances.

# Professor Messer 2.3 | Mobile Device Vulnerabilities

Mobile device security presents unique challenges because smartphones and tablets are portable, easily concealed, constantly mobile, and persistently connected to the internet. While they contain sensitive personal and corporate data, common user actions like bypassing operating system restrictions or installing unverified software can expose an organization to severe risk.

---

### 1. The Mobile Threat Profile

* **Physical Characteristics & Tracking:** Mobile devices are small, easily pocketed, and in constant transit, making physical tracking, asset auditing, and perimeter containment difficult.
* **Data Aggregation:** Devices host a combination of sensitive corporate resources (emails, internal apps, VPN profiles) alongside personal user data.
* **Persistent Connectivity:** Constant cellular and Wi-Fi connections make endpoints reachable from anywhere on the internet, creating ongoing opportunities for remote attacks.

---

### 2. Bypassing OS Security Controls: Jailbreaking & Rooting

> [!WARNING] Circumventing Built-in Protections
> Operating systems like iOS and Android enforce sandboxing and strict permission boundaries. Replacing the vendor firmware strips these security barriers away entirely.

* **Definitions:**
  * **Jailbreaking:** Modifying Apple iOS to bypass system restrictions and gain unrestricted OS-level access.
  * **Rooting:** Acquiring root superuser permissions on an Android operating system to modify protected files and settings.
* **Security Implications:**
  * Replaces stock firmware with custom third-party operating systems or binaries.
  * Completely bypasses enterprise controls enforced by Mobile Device Management (MDM) solutions.
  * Disables application sandboxing, enabling a single compromised app to access memory and data across all other installed applications.

---

### 3. Application Security & Sideloading

* **Sideloading:** Installing application packages (e.g., `.apk` or `.ipa` files) from third-party websites, unverified forums, or unauthorized marketplaces outside official platform channels.
* **Malware Exposure:** Bypassing vendor app store review pipelines drastically increases the likelihood of downloading spyware, Trojans, or unauthorized tracking software.
* **MDM & App Allowlisting:** Enterprise MDM solutions restrict app installations strictly to approved catalogs, such as official vendor app stores (Apple App Store, Google Play) or private enterprise app stores.

---

### 4. Administrative & Policy Controls

> [!IMPORTANT] Acceptable Use Policy (AUP) Enforcement
> Technical controls like MDM must be backed by formal organizational policies to deter unauthorized device modifications.

* **AUP Guidelines:** Corporate security policies should explicitly define acceptable mobile device configurations and prohibit rooting, jailbreaking, and sideloading.
* **Disciplinary Consequences:** Circumventing mobile security boundaries exposes the entire corporate perimeter to risk and is typically treated as a serious policy violation subject to disciplinary action or termination.


# Professor Messer 2.3 | Zero-day Vulnerabilities

A zero-day vulnerability is an undisclosed computer-software vulnerability that either has not been discovered by the software vendor or has been discovered by attackers before a security patch or mitigation exists. When adversaries actively exploit this unpatched flaw, it is known as a zero-day attack, leaving organizations vulnerable until defensive mitigations or vendor patches are engineered and deployed.

---

### 1. Dynamics of Zero-Day Flaws

* **Latent Flaws:** All complex software systems and operating systems contain undiscovered vulnerabilities within their codebase.
* **The Race Between Researchers and Attackers:**
  * **Ethical Researchers:** Discover vulnerabilities and privately disclose them to software vendors so fixes can be engineered before details become public.
  * **Adversaries:** Discover or purchase undisclosed vulnerabilities to quietly build exploit code, keeping the vendor unaware of the flaw's existence.
* **Lack of Remediation:** Because the vendor has zero knowledge of the issue, no official security patch exists at "day zero" of its active exploitation in the wild.
* **Scramble to Patch:** Once a zero-day exploit is identified in active attacks, vendors initiate emergency engineering cycles to publish an out-of-band security update.

---

### 2. Tracking Vulnerabilities (CVE)

> [!NOTE] Vulnerability Databases
> The cybersecurity community catalogs and standardizes public software flaws via the Common Vulnerabilities and Exposures (CVE) system, maintained by MITRE (`cve.mitre.org`).

---

### 3. Real-World Zero-Day Examples (Spring 2023)

> [!WARNING] Active Exploitation in the Wild
> Many zero-day vulnerabilities bypass core architectural security boundaries, requiring immediate emergency updates from major platform providers.

* **Google Chrome (April 2023):**
  * A zero-day involving memory corruption that enabled an attacker to achieve a browser **sandbox escape**, breaking out of client-side process isolation.
* **Microsoft Windows (May 2023):**
  * A vulnerability that allowed malicious, self-signed code to execute during the **UEFI boot process**, effectively bypassing hardware-rooted Secure Boot protections.
* **Apple iOS & iPadOS (May 2023):**
  * Three distinct zero-day patches were rushed to production addressing flaws actively exploited in the wild:
    * A **sandbox escape** flaw.
    * An **unauthorized disclosure** of sensitive system information.
    * An **arbitrary code execution** vulnerability.
