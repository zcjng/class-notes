## 📝 Raw Notes

### tcpdump
- `sudo tcpdump [-i interface] [option(s)] [expression(s)]`
- `-w` write to `.pcap`, `-r` read one back, `-c` packet limit, `-v` verbose, `-n`/`-nn` disable name/port resolution (avoids reverse DNS and speed loss).
- Output: timestamp, src/dst IP and port, IP version, TTL, fragmentation flags, protocol, checksum, TCP flags (PUSH/ACK).
- Filters combine with `and` / `or` / `not`: `port 443`, `host 10.0.0.5`, `ip6`, `src 10.0.0.5 and not port 22`.

### Detection & analysis
- Detection tools (IDS, SIEM) surface unusual activity from normal business events. An alert fires only when an incident is **suspected**.
- Analysis validates the alert — critical thinking plus IoC investigation — to confirm whether real unauthorised activity occurred.
- Hard truths: tools can't catch everything (limits + incomplete deployment), and alert volume is high because of misconfigured rules (false positives) or genuine spikes from new exploits.

### Threat hunting & intel
- **Threat hunting** = proactive human search for what automated tools miss (e.g. fileless malware). Blends analysis, intel, IoCs, ML.
- **Threat intelligence** = evidence-based context on TTPs from reports, advisories, feeds. **TIPs** aggregate and prioritize it.
- **Cyber deception**: honeypots are decoys — no legitimate user touches them, so any hit is high-signal.
- **Information vs. intelligence**: information is raw facts; intelligence is analysis that supports decisions.

### CI/CD monitoring
- IoCs: unexpected/late-night commits, unreviewed large deletions, anomalous deployment patterns, pipeline failures, compromised dependencies, hardcoded-secret exposure.
- Logging: execution/commit logs give a baseline; access/deployment logs track who released what.
- SIEM rules + ML detect known IoCs; continuous scanning gives real-time alerts on secret exposure and exploitable CVEs.

### IoCs vs. IoAs
- **IoC** = forensic artefact (hash, IP) → who/what, after the fact. **IoA** = behavioural evidence (unknown process opening a connection) → why/how, in real time.
- **Pyramid of Pain** (David J. Bianco), base → peak: hash values → IP addresses → domain names → network artefacts → host artefacts → tools → **TTPs**. Blocking the base is nearly free for the attacker to evade; blocking TTPs hurts most.
- Investigative tools: **VirusTotal**, Jotti's malware scan, Urlscan.io, MalwareBazaar. **ISACs** crowdsource threat data.
- Single IoCs mislead — always add threat-intelligence context.

### Documentation
- Why: **scalability** (ops beyond a few analysts), **standardization** (policies/processes/SOPs, consistent quality), **transparency** (evidence for insurance, regulatory and legal matters), and continuous maintenance as threats and regulations change.
- Best practices: tailor depth/language to the audience, state the purpose up front, review regularly, run post-incident reviews.

### Chain of custody
- Formal record of evidence possession and control: who handled it, why, when, where it moved.
- Write-protect media and hash it before handling. Document description (IPs, MACs) + transfer log.
- **Broken custody** (inconsistent or missing entries) can make evidence inadmissible.

### Playbooks
- Provide step-by-step instructions and checklists — structure during DDoS, ransomware or malware events.
- **Non-automated** (manual), **automated / semi-automated** (SIEM + SOAR, lower resolution time).
- Must be maintained; post-incident review is the natural time to update them.

### Triage
- Like ER triage: limited resources → worst first. Ransomware outranks one phishing email.
- Steps: **receive & assess** (false positive or not?) → **assign priority** (functional impact, information impact, recoverability) → **collect & analyse** → **escalate** if severe/complex.
- Benefits: resource management and a standard, consistent process.

### Containment → eradication → recovery
- **Containment**: limit damage; isolate affected devices.
- **Eradication**: remove all components/traces; vulnerability tests and patching.
- **Recovery**: restore operations; reimage, reset passwords, update firewall rules.
- **BCP** covers the whole business; **DRP** covers information systems after major failures/disasters.
- **Site resilience**: hot (ready now) → warm (quickly prepared) → cold (needs full setup).

### Post-incident
- **Final report**: 5 W's, timeline, findings, recommendations — written for both technical and executive readers.
- **Lessons learned meeting** within ~2 weeks: agenda, moderator, scribe, all parties. Focus on **discovery, containment, recovery, what to change** — *blame-free*.
- Output: prioritized fixes to playbooks, controls, training.

### Logs (M4)
- Logs answer what/where/when; analysis finds events of interest and troubleshoots.
- **Log forwarders** push data to a central repository; SIEM aggregates, normalizes, processes in real time.
- Sources: network devices, OSes, apps, security tools, authentication. Entry fields: action (e.g. ALLOW), source IP, timestamp.
- **Overlogging** → storage cost, degraded performance, hard-to-find events, PII compliance risk.
- Retention driven by **FISMA** (public), **HIPAA** (health), **PCI DSS** (finance). Centralize to prevent tampering.
- Formats: **JSON** (key-value/arrays/objects), **Syslog** (header + structured data + message), **XML** (tags), **CSV** (comma-separated, positional), **CEF** (pipe-separated: vendor, product, version, severity + key-value extensions, usually over Syslog).
- **Telemetry** = data collection/transmission (e.g. pcaps) used as evidence alongside logs.

### Detection methods (M4)
- **HIDS** on endpoints (files, resources, user activity); **NIDS** at network points (broad visibility). Together = layered defence.
- **Signature-based**: matches known patterns; low false positives; can't see zero-days or modified code; needs constant updates.
- **Anomaly-based**: baseline during training, alert on deviation; catches new threats; higher false positives; blind if the attacker was present during training.
